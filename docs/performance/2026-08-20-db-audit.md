# MMS — Database Audit (new-prod, 2026-08-20)

Read-only audit of the **live** database (`optishfnnctrhffpoywg`) via `psql`.
Scope: security (RLS, function exposure), schema hygiene (keys, constraints),
performance (indexes, bloat), and maintenance.

The database is in **good, professional shape**. Foundations are all correct:

| Check | Result |
|---|---|
| Public tables | 111 |
| **RLS enabled** | **111 / 111 (100%)** ✅ |

## Issues, by priority

### 🟠 1. Anon-callable SECURITY DEFINER functions — 2 leak data (fix before fully live)

29 SECURITY DEFINER functions are executable by the **`anon` role** — i.e. callable
by anyone holding the public anon key (which ships in the browser bundle). SECURITY
DEFINER runs with elevated privileges and **bypasses RLS**, so the only thing
protecting them is a check inside the function body.

I checked each one:

- **14 write/report RPCs self-check auth** (`rpc_delete_customer_payment`,
  `rpc_edit_*_payment`, `rpc_report_pnl_fx_detail`, `rpc_create/accept_custody_assign`,
  `rpc_archive_inventory_category`, `rpc_*_po_approval_steps`, `rpc_request_warehouse_item`,
  `rpc_resolve_item_request`, `rpc_update_inventory_sort_orders`, `is_any_division_visible`).
  An anon call fails their internal check → **not exploitable today**. But they rely
  solely on that check — one future edit that drops it = an open endpoint.

- **2 readers have NO auth check and leak data** ⚠️ — these are the real finding:
  - **`get_custody_master_list`** → returns every custody location across all
    divisions **including responsible-person names and phone numbers** (PII).
  - **`get_category_stock_aggregates`** → returns stock quantities / values.
  Both are called only from authenticated app screens, so anon has no reason to reach
  them.

- **`resolve_login_email`** is **intentionally** anon-callable — login resolves
  username→email *before* authentication (`login/page.tsx`, `login/actions.ts`). Keep
  its anon grant. (It is a username→email enumeration vector; inherent to username
  login — mitigate with edge rate-limiting if desired, otherwise accept.)

- The rest are trigger functions (can't be invoked as RPCs anyway) + helpers.

**Fix:** a migration that `REVOKE EXECUTE ... FROM anon, public` on the SECURITY
DEFINER functions in `public` and `GRANT EXECUTE ... TO authenticated, service_role`
— **excluding `resolve_login_email`**. This closes the two leaks and makes the rest
defense-in-depth (matches the pattern the newer RPCs already use). Low-risk,
reversible, no app-code change.

### 🟡 2. 140 foreign keys without a covering index (no impact yet — index before growth)

140 FK columns have no index. Postgres does **not** auto-index FK columns, so joins
and cascade checks on them fall back to sequential scans. Today every table is tiny
(≤1,037 rows), so there is **zero measurable impact now**. It matters as transaction
volume grows.

Index the **hot-path** ones first (queried on every stock/consumption operation):

- `fifo_cost_layers (warehouse_id)`, `fifo_cost_layers (sub_container_id)`
- `inventory_stock_movements (warehouse_id)`, `inventory_stock_movements (sub_container_id)`
- `consumption_entries (source_warehouse_id, consumer_sub_container_id, discipline_id, milestone_id)`
- `cogs_entries (consumer_sub_container_id, consumer_customer_id)`
- `inventory_damaged_stock (brand_variant_id)`, `inventory_damaged_stock_layers (brand_variant_id)`

The many `created_by` / `uploaded_by` / `reviewed_by` audit FKs are **low priority**
(rarely filtered) — index them only if an audit-by-user report gets slow.

### 🟢 3. Two tables have RLS on but no policy (verify intentional)

`consumption_number_counters` and `storage_cleanup_failures` have RLS enabled with
**no policy** → deny-all to `anon`/`authenticated`, reachable only through SECURITY
DEFINER RPCs / `service_role`. For internal counter/log tables this is the correct,
safe pattern (deny-by-default). **Almost certainly intentional** — just confirming
nothing is meant to read them directly.
