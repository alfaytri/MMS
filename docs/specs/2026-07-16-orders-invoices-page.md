# Spec — Orders Invoices Page (`/invoices`)

**Date:** 2026-07-16
**Author:** Ismail (product) / Claude (spec)
**Status:** Approved for implementation — pending user confirmation of Q1–Q3 below

---

## 1. Context & Why

The `/invoices` page must show **invoices generated from the Orders module** (team-leader invoices created when a team completes a visit). It is **NOT** the same page as `/sales/invoices` — that page belongs to the Sale Orders (Purchase & Sales) module.

The current `/invoices` page (as of this session) mistakenly queries the `invoices` table filtered by `direction='ar'`, `source='order'`. That query returns **Sale Order invoices**, not Orders module invoices, because sale-order invoices are inserted into `public.invoices` with `source='order'` by [`invoiceSync.ts`](src/lib/invoiceSync.ts) and the SQL RPC in [20260627104000_relax_so_invoice_gate.sql](supabase/migrations/20260627104000_relax_so_invoice_gate.sql).

Orders module invoices live in a **completely separate table**: `public.tl_invoices` (created by [TlInvoiceDialog.tsx](src/components/team-leader/TlInvoiceDialog.tsx) when a team leader confirms a completed visit).

## 2. Business Requirements (from user)

1. When a team completes an order, an invoice PDF is generated (same look-and-feel as the confirmation-order PDF, but showing amounts owed + amounts paid).
2. On the `/invoices` page, each card displays:
   - Invoice number, customer name/phone, order reference, total, status
   - **View PDF** button
   - **View Payments** button — opens a dialog listing each payment record with: Payment Type (method), Payment Date, Payment Time, Registered By, Amount, Notes
   - **Register Payment** button — opens a dialog to enter amount (full or partial) + payment method → creates a payment record. The current user's name is stored as `Registered By` (e.g., team leader entering cash/POS in the field).
3. The list must be filterable by status, date range, customer, agent — but **not by source** (since this page is dedicated to Orders invoices only).

## 3. Data Model — Current vs Required

### Current `tl_invoices` schema (baseline)

```sql
CREATE TABLE public.tl_invoices (
  id                 uuid PK,
  invoice_number     text NOT NULL,           -- auto-generated by DB trigger
  visit_id           uuid NOT NULL,           -- links to visits/site_visits
  order_id           text,                    -- app-visible order display string
  customer_name      text NOT NULL,
  customer_phone     text,
  items              jsonb DEFAULT '[]',      -- deprecated (replaced by tl_invoice_lines)
  subtotal           numeric NOT NULL DEFAULT 0,
  discount_amount    numeric NOT NULL DEFAULT 0,
  total_amount       numeric NOT NULL DEFAULT 0,
  payment_method_id  uuid,
  payment_status     text DEFAULT 'unpaid',   -- CHECK ('unpaid','paid') — NO 'partial'
  dibsy_payment_id   text,
  dibsy_checkout_url text,
  notes              text,
  created_by         uuid,                    -- FK to profiles(id) — this becomes "Registered By" for the FIRST payment
  created_at         timestamptz,
  updated_at         timestamptz
);
```

`tl_invoice_lines` (line items) exists — see migration `20260715160000_normalize_remaining_json_columns.sql`.

### Missing pieces

1. **No `tl_invoice_payments` table.** Currently `payment_status` is a single flag with no history. To support partial payments + multiple entries + audit ("Registered By"), we need a new table.
2. **`payment_status` CHECK constraint** must be relaxed to allow `'partial'`.

### Required migration (`tl_invoice_payments` + status widen)

```sql
-- 1. Widen tl_invoices.payment_status
ALTER TABLE public.tl_invoices
  DROP CONSTRAINT IF EXISTS tl_invoices_payment_status_check;
ALTER TABLE public.tl_invoices
  ADD CONSTRAINT tl_invoices_payment_status_check
  CHECK (payment_status = ANY (ARRAY['unpaid','partial','paid']));

-- 2. New payments table
CREATE TABLE public.tl_invoice_payments (
  id                 uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  tl_invoice_id     uuid NOT NULL REFERENCES public.tl_invoices(id) ON DELETE CASCADE,
  amount             numeric NOT NULL CHECK (amount > 0),
  payment_method_id  uuid REFERENCES public.payment_methods(id),
  method_slug        text,                             -- denormalized for fast filtering
  paid_at            timestamptz NOT NULL DEFAULT now(),
  registered_by      uuid REFERENCES public.profiles(id),
  registered_by_name text,                             -- snapshot of profile.full_name at time of registration
  notes              text,
  created_at         timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_tl_invoice_payments_invoice ON public.tl_invoice_payments(tl_invoice_id);
CREATE INDEX idx_tl_invoice_payments_paid_at ON public.tl_invoice_payments(paid_at DESC);
ALTER TABLE public.tl_invoice_payments ENABLE ROW LEVEL SECURITY;

-- 3. RLS policies (mirror tl_invoices policies)
CREATE POLICY "Authenticated read tl_invoice_payments"
  ON public.tl_invoice_payments FOR SELECT TO authenticated USING (true);
CREATE POLICY "Authenticated insert tl_invoice_payments"
  ON public.tl_invoice_payments FOR INSERT TO authenticated WITH CHECK (true);

-- 4. Trigger to keep tl_invoices.payment_status + paid_amount in sync
--    (a) add tl_invoices.paid_amount numeric NOT NULL DEFAULT 0
--    (b) recompute on INSERT / UPDATE / DELETE of tl_invoice_payments
ALTER TABLE public.tl_invoices
  ADD COLUMN IF NOT EXISTS paid_amount numeric NOT NULL DEFAULT 0;

CREATE OR REPLACE FUNCTION public.sync_tl_invoice_paid_amount() RETURNS trigger AS $$
DECLARE
  v_invoice_id uuid := COALESCE(NEW.tl_invoice_id, OLD.tl_invoice_id);
  v_paid       numeric;
  v_total      numeric;
BEGIN
  SELECT COALESCE(SUM(amount),0) INTO v_paid
    FROM public.tl_invoice_payments WHERE tl_invoice_id = v_invoice_id;
  SELECT total_amount INTO v_total
    FROM public.tl_invoices WHERE id = v_invoice_id;

  UPDATE public.tl_invoices
     SET paid_amount    = v_paid,
         payment_status = CASE
                            WHEN v_paid <= 0            THEN 'unpaid'
                            WHEN v_paid >= v_total      THEN 'paid'
                            ELSE 'partial'
                          END,
         updated_at     = now()
   WHERE id = v_invoice_id;
  RETURN NULL;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER tl_invoice_payments_sync
AFTER INSERT OR UPDATE OR DELETE ON public.tl_invoice_payments
FOR EACH ROW EXECUTE FUNCTION public.sync_tl_invoice_paid_amount();
```

Migration filename: `supabase/migrations/YYYYMMDDHHMMSS_tl_invoice_payments.sql` — apply with `npx supabase db push`.

- `src/hooks/useInvoices.ts` — the `useRegisterInvoicePayment` mutation, the `payments(... agent_name, created_at)` join expansion, and the `FinanceInvoice.payments` type additions were made for AR invoices. - `src/components/invoices/RegisterPaymentDialog.tsx` — writes to `payments` table with `CPAY-XXXXX` IDs. Keep for `/sales/invoices` only.
- `src/components/invoices/ViewPaymentsDialog.tsx` — reads `invoice.payments` (joined from `payments` table). Keep for `/sales/invoices` only.
- `src/app/(dashboard)/invoices/page.tsx` — currently filters `source: 'order'` on the AR `invoices` table. **Fully replace** this page against `tl_invoices`.

Decision needed (Q1 below): reuse the same components for both pages, or split them?

### Phase C — Build the new `/invoices` page against `tl_invoices`

Files to create:

6. **`src/app/api/orders/invoices/[id]/pdf/route.ts`** — new PDF endpoint. Model after [`src/app/api/orders/[id]/generate-confirmation-pdf/route.ts`](src/app/api/orders/[id]/generate-confirmation-pdf/route.ts). Layout should mirror the order-confirmation PDF but add:
   - Total, Paid, Remaining sections
   - Line items from `tl_invoice_lines`
   - Payment history table from `tl_invoice_payments` (optional — may be split into a separate "Payment Receipt" PDF later; user to clarify)

### Phase D — Auto-generate PDF on order completion

Add to `TlInvoiceDialog.handleConfirm()` after the successful invoice insert:
```typescript
await fetch(`/api/orders/invoices/${invoiceId}/pdf`, { method: 'POST', headers: { Authorization: `Bearer ${session.access_token}` } })
```
Store the returned public URL in `tl_invoices.pdf_url` (new column) or regenerate lazily on demand — matches sales-invoice pattern.

## 5. Open Questions (need user answers before coding)

- **Q1** — Should `InvoiceCard` / `RegisterPaymentDialog` / `ViewPaymentsDialog` be **duplicated** into new tl_invoice-specific components under `src/components/orders-invoices/`, or **generalised** to work with both AR invoices AND tl_invoices? Recommendation: duplicate — the data shapes are too different, sharing will create abstraction burn.
- **Q2** — Should partial payments be allowed to exceed `total_amount`? Recommendation: no, enforce in the mutation (return error if `sum(payments) + newAmount > total_amount`).
- **Q3** — On the PDF: does the user want ONE combined "Invoice with payment status" PDF, or a separate "Payment Receipt" PDF each time a payment is registered? Recommendation: combined for now, keep it simple.

## 6. Rollback / Cleanup Notes

- Delete the (unused) `tl_invoice_payments` migration

This is the "big refactor" path and NOT recommended right now — the tl_invoices table is already wired into calendar / team-leader / dibsy flows.
